For the **single-player version**, I would implement the NPC/wildlife system in the following pieces. Keep the code structured so that later the simulation can move to a server, but **do not build multiplayer/network synchronization yet**.

## 1. Entity system

Create a generic living-entity structure.

Each entity needs:

* `id`
* `type`
* `species`
* `position`
* `direction`
* `speed`
* `state`
* `target`
* `health`
* `hunger`
* interaction properties
* animation state

Example:

```text
Animal
├── id
├── species
├── position
├── direction
├── movement
├── behaviorState
├── needs
└── interactionState
```

Every entity gets a unique small integer ID.

---

# 2. `generateRandom(id)`

Create one centralized random-generation function.

Every random decision in the NPC/wildlife system must go through it.

Use it for:

* spawn decisions
* group sizes
* initial position variation
* idle duration
* wandering duration
* wandering direction
* wandering distance
* eating decisions
* choosing whether to continue eating
* future AI decisions

Do **not** use `Math.random()` directly inside animal/NPC logic.

The important reason is that later you can make the simulation deterministic/server-controlled much more easily.

---

# 3. Species configuration

Don't hardcode behavior separately for every animal.

Create configuration for each species.

For example:

```text
Cow
├── movementSpeed
├── preferredEnvironment
├── food
├── groupSize
├── idleTime
├── wanderTime
├── wanderRadius
├── canPet
└── canFeed
```

Then:

```text
Sheep
Rabbit
Chicken
Deer
```

can use the same generic animal system with different parameters.

---

# 4. World environment detection

Since there is only one biome, don't create a complicated biome system.

The world has:

```text
Grassland
Water
Village
```

And derive:

```text
Jungle
```

when a tree cluster contains **20 or more trees**.

So animals can query something like:

```text
getEnvironmentAt(x, y)
```

and receive information about their surroundings.

Example:

```text
grass: true
water: false
village: false
denseTrees: true
```

---

# 5. Wildlife spawn system

Implement a wildlife population manager.

Its job:

```text
check area
    ↓
determine desired population
    ↓
find valid spawn location
    ↓
choose species
    ↓
create animal
```

Spawn rules should consider:

* valid terrain
* grass availability
* jungle/dense-tree area
* distance from player
* existing population
* species-specific rules
* group size

---

# 6. Animal groups

Animals shouldn't always spawn individually.

For example:

```text
Cow
 ├── Cow #101
 ├── Cow #102
 ├── Cow #103
 └── Cow #104
```

When a group is spawned:

1. Choose a group center.
2. Generate group size.
3. Find nearby valid positions.
4. Spawn animals around the center.

Each animal still has its own unique ID.

Initially, animals don't need sophisticated flocking.

They can simply remain within a loose distance of the group.

---

# 7. Spawn/despawn management

Maintain an active wildlife population around the player.

Conceptually:

```text
Player
   ↓
active simulation radius
   ↓
animals inside → active
animals far away → inactive/despawned
```

For now, because this is single player, you can simply remove animals that get sufficiently far away.

Later, this can become a proper server-side entity activation system.

# 9. Idle behavior

When an animal is idle:

```text
Animal stands still
       ↓
wait random duration
       ↓
make decision
```

The decision comes from:

```text
generateRandom(animal.id)
```

Possible result:

```text
remain idle
```

or:

```text
start wandering
```

This prevents every animal from constantly moving.

---

# 10. Wandering

Basic logic:

```text
IDLE
 ↓
choose random nearby target
 ↓
validate target
 ↓
WANDER
 ↓
walk toward target
 ↓
target reached
 ↓
IDLE
```

The target should be relatively close.

For example:

```text
current position
       ↓
random point 3–7 tiles away
```

Don't make animals randomly travel hundreds of tiles.

---

# 11. Movement

Use simple target-based movement.

Conceptually:

```text
direction = normalize(target - position)

position += direction × speed × deltaTime
```

When sufficiently close:

```text
target reached
```

then:

```text
state = IDLE
```

No complex pathfinding initially.

---

# 12. Movement collision

Animals should respect the world.

They shouldn't walk through:

* water
* buildings
* mountains/blocked terrain
* map boundaries
* other non-walkable objects

Before moving:

```text
isWalkable(nextPosition)
```

If false:

```text
stop
choose another target
```

---

# 13. Animal direction

Calculate direction from movement.

```text
dx = targetX - x
dy = targetY - y
```

Then determine:

```text
UP
DOWN
LEFT
RIGHT
```

This feeds directly into the sprite animation system.

---

# 14. Walking animation

When:

```text
state == WANDER
```

play:

```text
walk animation
```

When:

```text
state == IDLE
```

play:

```text
idle animation
```

Animation should be completely separate from movement logic.

---

# 15. Grass detection

Animals that eat grass should periodically check their surroundings.

Conceptually:

```text
Animal
 ↓
Is grass nearby?
 ↓
Yes
 ↓
Is hunger high enough?
 ↓
Yes
 ↓
move toward grass
```

Once sufficiently close:

```text
state = EATING
```

For the first version, you can simply search for the nearest suitable grass position within a small radius.

# 16. Eating behavior

When eating:

```text
Animal stops moving
```

Then:

```text
EATING
   ↓
slow vertical bob
   ↓
wait
   ↓
finish eating
   ↓
IDLE
```

The vertical movement is **visual animation**, not actual world movement.

For example:

```text
Y
│
│    /\ 
│   /  \
│__/    \__
```

Very small and slow.

---

# 17. Eating animation

While eating:

```text
baseY - smallOffset
baseY
baseY + smallOffset
baseY
```

Use a smooth oscillation rather than abruptly changing position.

The animal should look like:

```text
🐄
 ↓
dip
 ↓
rise
 ↓
dip
 ↓
rise
```

The actual logical position remains unchanged.

---

# 18. Hunger

Give animals a basic hunger value.

For example:

```text
hunger = 0 → not hungry
hunger = high → wants food
```

Over time:

```text
time passes
    ↓
hunger increases
```

When hunger reaches a threshold:

```text
animal prioritizes eating
```

This means animals aren't constantly stopping to eat.

---

# 19. Grass consumption

For the initial implementation:

```text
Animal eats grass
```

doesn't necessarily have to destroy the grass.

Just use:

```text

→ eating animation
→ hunger reduced
```

Later you can make grass temporarily disappear and regenerate.

# 27. Animal interaction priority

When multiple things could happen, give them priority.

For example:

```text

  ↑

  ↑
  │

  ↑
  │

```

So:

```text

        +

        ↓

        ↓

```

This prevents conflicting behaviors.

# 31. Rendering/animation separation

Keep these three things separate:

```text
GAME LOGIC
    ↓
logical position/state

MOVEMENT
    ↓
position changes

RENDERING
    ↓
sprite + animation + effects
```

For example, eating:

```text
Game state:
    animal.state = EATING

Movement:
    no movement

Renderer:
    eating bob animation
```

Petting:

```text
Game state:
    animal.state = PETTED

Movement:
    stopped

Renderer:
    hearts
    animal reaction
    player hop
```

This separation will make the multiplayer conversion much easier later.

---

# 32. Update loop

The NPC manager can run something like:

```text
NPC UPDATE
│
├── update needs
│
├── update state timers
│
├── make behavior decisions
│
├── calculate movement
│
├── check collisions
│
├── check interactions
│
└── update animation state
```

But don't make every animal perform expensive calculations every frame.

---

# 33. Update frequency

Rendering might run at:

```text
60 FPS
```

but behavioral decisions don't need to.

For example:

```text
60 FPS
    → movement/rendering

5–10 times/sec
    → behavior decisions

occasionally
    → spawning/population management
```

This will let you have many animals without unnecessarily consuming CPU.

A top-down, browser-based, Minecraft-inspired survival sandbox set in a procedurally generated grassland world, with jungle regions formed by dense tree clusters, water, villages, wildlife, NPCs, gathering, crafting, building, exploration, combat, survival, and progression.

It is single-player now, but every gameplay system should be structured so that multiplayer/server authority can be introduced later.

The most important design decision

I would not build this as "Minecraft but top-down" mechanically. Use Minecraft's survival sandbox philosophy, but give your game its own identity through:

Living wildlife
       +
Village NPC ecosystem
       +
Exploration
       +
Procedural world
       +
Building
       +
Survival
       +
Animal relationships
       +
Emergent events

And for the code architecture, make Game State + Systems + Events the backbone:

                 INPUT
                   ↓
             ┌───────────┐
             │  SYSTEMS  │
             └─────┬─────┘
                   ↓
              GAME STATE
                   ↓
                EVENTS
             ┌─────┴─────┐
             ↓           ↓
          RENDER       AUDIO/VFX

That architecture is suitable for the single-player game right now, while keeping the eventual transition to:

Client → Socket.io → Authoritative Server → State → Clients

reasonably clean rather than requiring a rewrite of the entire game.
